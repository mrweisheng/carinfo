## 1. 现状：这套逻辑在做什么

### 1.1 两套键（设计正确，实测支撑充分）

| 键 | 用途 | 实测理由 |
|---|---|---|
| `base_model`（车系） | **匹配**——搜「阿尔法」要能搜到 ALPHARD / ALPHARD 3.5 / ALPHARD SA VELLFIRE | ALPHARD 一车系有 **293 种写法**；归一后候选从 64.2% → 94.0% |
| `(base_model, year_bucket)` | **比价**——价格基准必须同类同代 | ALPHARD 按年代差 **10 倍**（2025-2029 中位 64.8 万 vs 2005-2009 中位 3.98 万）；按排量只差 21% 且方向反直觉 |

实测行情表（ALPHARD）：

```
      年份段     样本          P25          中位           P75
  2005-2009      13       38,000       39,800       44,800
  2010-2014     132       47,575       58,944       83,800
  2015-2019     748      205,000      248,888      298,000
  2020-2024     853      358,001      398,800      530,000
  2025-2029     305      598,005      648,008      696,000
```

「缺维从分母里去掉」这个决策是对的。实测对照 ⚠️（左两列是 **ALPHARD 2,052 台候选**，

| condition | 0.873 | 0.206 | **0.750** | 0.246 |
| heat | 0.627 | 0.163 | 0.646 | 0.164 |
| near | 0.525 | 0.358 | — | — |

> ⚠️ 原报告只给了左两列却没标口径，容易被误读成全库。两者在 `condition` 上差 **0.12**

**但要如实指出**：缺维归一**并没有完全消除偏差**。实测 ALPHARD 2,052 台候选中：

**结论**：缺维归一的方向正确，但「数据齐全度」仍在实质影响排序，属于**已知残留偏差**。

## 2. P0 缺陷

### D-1 · 时效维在量「抓取批次」而不是「挂牌时长」🔴

**证据链**：

**① `age_days` 分布有硬断层**，21–161 天区间**一台车都没有**：

```
  age_days=   0:   639       age_days=  20:    49
  age_days=   1:  1659       ─────────── 断层 141 天 ───────────
  age_days=   2:  1339       age_days= 162:   613
  age_days=   3:   921       age_days= 163:   467
  age_days=  19:   156       age_days= 164:   437
                    ↑                           ↑
              最近一批抓取                 上一批抓取
```

**21–161 天之间：0 台。** `age_days` 在 21,496 台车里只有 **124 个不同取值**。

**② `update_date` 本身只有 123 个不同日期**，取值高度集中在几个批次上：

```
  2026-09-23   1,800 台     ← 09-24 那轮爬虫（7180 台）写的
  2026-09-22   1,325 台
  2025-08-16   1,035 台     ← 141 天断层就在这
  2026-09-21     887 台
  2026-03-10     701 台     ← 迁移日
  2026-09-25     639 台     ← 今天那轮（1000 台）
```

**③ `crawl_logs` 佐证这是批次行为**：

```
  2026-09-25  轮数=1  总台数=1000    ← 今天
  2026-09-24  轮数=1  总台数=7180    ← 昨天（大规模）
  2026-04-15  轮数=1  总台数=800     ← 4 月每天 800 台
  2026-04-14  轮数=1  总台数=800
  ...
  2026-03-25  轮数=1  总台数=800
```

**根因**：`features.py:load_rows()` 用 `COALESCE(update_date, created_at)` 算 `age_days`。而 `update_date` 是**站点详情页的「更新日期」**——爬虫每到一次就刷新一次。于是 ⚠️：

- 一辆在售 2 年的车，只要今天被爬到，`age_days = 1`，时效分 **1.00**（满分）
- 一辆真正刚挂牌的车，如果今天没爬到，`age_days = 162`，时效分 **0.29**

（原报告写 0.90 / 0.25 均不准：`FRESH_ANCHORS` 首档是 `(3, 1.00)`，`age_days ≤ 3` 一律钳到满分；162 天落在 `(90,0.45)→(180,0.25)` 的插值上，算出 0.29 而非 0.25。）

**后果**：时效维（权重 0.16）实际在奖励「**最近被爬到的**」而不是「**刚挂牌的**」。实测 `age_days` 分段 ⚠️：

```
   0-  3 天   4,558 台  21.2%   时效分 1.00        ← 最近一批抓到的
   4-  7 天   2,267 台  10.5%   时效分 0.98→0.90
   8- 30 天   3,067 台  14.3%   时效分 0.89→0.70
  31- 90 天       0 台   0.0%   ← 断层
  91-180 天   5,071 台  23.6%   时效分 0.45→0.25
 181-404 天   6,533 台  30.4%   时效分 ≤0.25
```

> **54.0% 的车（11,604 台）时效分 ≤ 0.45，其中 30.4%（6,533 台）≤ 0.25。**
> ⚠️ 原报告写「26% 的车拿低时效分」，那是按爬虫覆盖率推算的，**实测翻了一倍**。
> 这个维度不是"影响一部分车"，而是在**系统性惩罚过半数的库存**。

而每日抓取量本身就极不均匀（`crawl_logs` 实测）：

```
  2026-09-25   1 轮   1,000 台
  2026-09-24   1 轮   7,180 台
  2026-04-15   1 轮     800 台   ← 4 月期间每天 800
  2026-04-07   1 轮     789 台
```

抓取节奏一变，同一台车的时效分就跳档 —— **这个维度带有强噪声**，不只是语义错。

**FRESH_ANCHORS 存在死区** ⚠️：`(30, 0.70)` → `(90, 0.45)` 这段插值对应 `age_days` 31–90 天，而该区间**实测 0 台车**。锚点表在这里从未被执行：

```
age_days ≤ 3    → 1.00        （4,558 台，钳制在上限档）
age_days 4–20   → 0.98 → 0.79 （5,334 台，走插值）
age_days 31–90  → 从未使用     （0 台）
age_days ≥ 91   → ≤0.45       （11,604 台，钳制在下段）
```

（原报告说「`(3,1.00),(7,0.90),(30,0.70)` 三档根本没被用到」不准确 —— 前三档都有数据落在上面，真正没用到的是 `(30,0.70)` 与 `(90,0.45)` **之间**的那段。）

**影响面**：所有查询，无一例外（`fresh` 覆盖 100%，没有车能靠缺维躲开）。这是**权重第二高的实质维度**（0.16），却在用一个与语义不符、且带强噪声的量。

### D-2 · 「左右」near 维不是软偏好，而是准硬过滤 🔴

**设计意图**（代码注释写得很清楚）：

> 「左右」是偏好，不是约束……绝不产生 `price_min/max`。理由：硬切会把 39 万、62 万的车直接删掉，而用户本意只是"离得近的排前面"——不可逆。

**设计意图正确，且代码确实没产生硬过滤**——实测确认 `build_query()` 里 zero 出现 `price_min/price_max`：

```
SQL 片段: [' v.current_price IS NOT NULL ', ' v.current_price > 0']
params:   ['ALPHARD', 1]          ← 只有车型和 vehicle_type，没有价格边界 ✓
```

**但权重配置让「软偏好」退化成了「准硬过滤」**：

near 给了 **0.20** 权重，与性价比**完全等权**。而它的取值分布是**极端两极**的：

```
「50万左右的阿尔法」实测 2,046 台候选（默认剔除异常车）：
   near = 0（完全超出衰减带）  325 台  15.8%   ← 直接丢掉 0.20
   near = 1（带内）            264 台  12.9%   ← 白拿 0.20
   0 < near < 1（衰减中）    1,463 台  71.3%

near 标准差 0.358 —— **仅次于 fresh（0.362），是所有维度里第二高**
                     （value 0.275 / condition 0.206 / heat 0.163）
```

> ⚠️ 原报告称 near 标准差「是所有维度里最高」，但同一句话的括号里就列着
> `fresh 0.362 > 0.357` —— 自相矛盾。near 是**第二高**，而 fresh 高是因为
> 它量错了东西（见 D-1），两者都不该拿高分。

**实测价格响应曲线**（说「50万左右」时）：

```
   128,000 元 → near=0.000     ← ratio 0.51，真正的捡漏
   250,000 元 → near=0.400
   400,000 元 → near=1.000     ← 带内
   500,000 元 → near=1.000     ← 锚点
   600,000 元 → near=0.600
   800,000 元 → near=0.000
```

**决定性证据——Top10 完全换血**：

```
无锚点 Top10                                    有「50万左右」Top10
1.0000 2018 ALPHARD SA VELLFIRE  HK$128,000     0.9771 2025 ALPHARD 40       HK$528,000
0.9944 2010 ALPHARD              HK$ 30,000     0.9754 2025 ALPHARD          HK$478,000
0.9921 2022 ALPHARD 8            HK$239,000     0.9702 2025 ALPHARD2.5Z      HK$522,000
0.9894 2020 ALPHARD 2.5 FC       HK$229,000     0.9702 2025 ALPHARD 2.5 Z M  HK$548,009
0.9888 2021 ALPHARD 2.5 FC       HK$228,000     0.9699 2025 ALPHARD 2.5 Z    HK$548,000
0.9874 2020 ALPHARD 2.5 SC FC    HK$248,800     0.9697 2025 ALPHARD 2.5 Z VE HK$548,009
0.9863 2020 ALPHARD 3.5 GF FC    HK$278,888     0.9678 2025 ALPHARD 2.5 Z    HK$548,008

0.9843 2013 ALPHARD 2.4          HK$ 37,300     0.9553 2025 ALPHARD 2.5 Z    HK$508,000

Top10 重合度：0 / 10
```

**问题不在「返回了 50 万的车」**（那是合理的）。问题在于 ⚠️：

> **ratio 0.509（便宜 49%）、无锚点时综合分 0.9944（第 2 名）的那台 2010 ALPHARD
> （HK$30,000），加锚点后掉到第 848 名。**

（原报告写「第 100 名开外」，实测是 **848**，比原描述严重得多 —— 实际上等于
从用户视野里彻底消失，不是"往后挪了挪"。）

用户说「50 万左右」是在**限定预算区间**，不是在说「我不在乎性价比」。而现在 near 独占总权重的 20%，其余五维的相对权重被整体乘 0.80，**等于性价比的相对话语权从 0.20 掉到 0.16**——比车况（0.12）只高一点。

这与代码注释里引用的原则**自相矛盾**。注释本身写着：

> Google Cloud 官方做法把这类条件归入 soft filter（boost）而非 hard filter，理由是"硬过滤在排序之前就砍掉候选池，排序无法挽回"

**soft filter / boost 的本意是小权重加成，不是与原维度等权。** 现在 near 的权重（0.20）等于性价比（0.20）、高于时效（0.16）和车况（0.12）——这是一个 boost 该有的量级吗？

**补充问题：权重缩放论证有漏洞**

代码注释声称：

```
缺维从分母去掉之后，没有「左右」的查询 near 缺席，加权平均 =
  Σ(0.8·wᵢ·sᵢ) / Σ(0.8·wᵢ) = Σ(wᵢ·sᵢ)   ← 与旧口径数学上完全等价
```

**这个等式在数学上成立，但结论被误用了。** 它只证明了「**无锚点时**新旧口径等价」——这是对的。但它被当成了「near 不影响既有查询」的证明，而实际上 near 影响的是**有锚点的查询**，那正是它存在的唯一场景。等价性只保证了**向后兼容**，没有为 0.20 这个权重提供任何依据。

## 3. P1 缺陷

### D-3 · 性价比维没有「便宜得可疑」的下限惩罚

`VALUE_ANCHORS` 的第一档是：

```python
(0.60, 1.00),   # 便宜 40%+  →  满分
```

`_interp()` 对 `x <= anchors[0][0]` 直接返回 `anchors[0][1]`，即 **ratio ≤ 0.60 一律给 1.00 满分**：

```
ratio=0.60 → 1.00
ratio=0.30 → 1.00   ← 和上面同分
ratio=0.05 → 1.00   ← 还是同分
```

`ANOMALY_RATIO = 0.5` 做了硬剔除（实测 `ratio<0.5 AND NOT is_anomaly = 0` 台，**剔除是生效的**）。但 **0.50–0.60 这段是盲区**：

```
0.50 <= ratio < 0.55:   265 台
0.50 <= ratio < 0.60:   626 台   ← 未剔除，且拿满分
0.50 <= ratio < 0.65: 1,120 台
0.50 <= ratio < 0.70: 1,736 台
```

实测这批车的成色（ALPHARD 2015-2019 段，中位 24.9 万）：

```
ratio=0.474 2016 ALPHARD              HK$118,000  手数=1  里程=-       行水=-
ratio=0.482 2016 ALPHARD              HK$120,000  手数=-  里程=-       行水=-
ratio=0.482 2017 ALPHARD 350          HK$120,000  手数=-  里程=180998  行水=-
ratio=0.502 2016 ALPHARD 2.5          HK$125,000  手数=0  里程=13000   行水=-
ratio=0.514 2018 ALPHARD SA VELLFIRE  HK$128,000  手数=0  里程=-       行水=-
```

**关键观察**：这些车 ratio 极低，但**车况数据（手数/里程/行水货）大多为空**。也就是说「便宜 49%」这个结论**无法用车况数据解释**——引擎无法区分它是"真捡漏"还是"有隐情"，却一律给满分并推到首位。

> ⚠️ 这里有个**商业风险**：如果这些是事故车/问题车，把它们作为"最优推荐"给客户，损害的是明哥中港牌的口碑。而 `is_anomaly` 的 0.5 阈值是拍的，没有数据依据支撑。

### D-4 · 车况维把「行货/水货」算成车况

```python
CONDITION_WEIGHTS = {"hand": 0.45, "mileage": 0.35, "import": 0.20}
IMPORT_SCORE = {"行貨": 1.0, "水貨": 0.70}
```

`import_type`（行货/水货）是**来源属性**，不是车况。把它算进「车况分」的后果：

- 一台**只填了「行貨」**、没有手数、没有里程的车 → `condition_score = 1.000`
- 一台「0 手 + 低里程 + 行货」的车 → `condition_score = 1.000`
- **两者同分**

实测：

```
车况满分(>=0.999)的车: 6,473 / 车况有值 17,598 台 = 36.8%
其中没有手数数据的:    1,224 台（19% 的满分车只有行货一项就拿了满分）

实测「只有行水货一项」的车：
   只有 行貨 → 车况分=1.000   998 台
   只有 水貨 → 车况分=0.700    12 台
```

**1,000 台车凭「行貨」两个字拿到车况满分**，而车况维权重 0.12——这些车凭空多拿了 0.12 分，压过那些有真实里程/手数但数据不完整的车。

另外 `IMPORT_SCORE` 里 `行貨: 1.0` 意味着行货车比水货车**无条件高 0.30×0.20 = 0.06 分**。行货保值更好是事实，但它应该是**独立的加分项**，不是「车况」的一部分——否则用户看到「车况分 1.000」会误以为车况被核实过。

## 4. 逻辑链完整性检查（哪些环节是漏的）

| 环节 | 现状 | 评价 |
|---|---|---|
| 用户意图 → SearchSpec | LLM + 规则双路径，白名单+值收敛+键归一 | ✅ 扎实 |
| 车型归一 | 四级路径，99%+ 命中 | ✅ 扎实 |
| 硬过滤 | 参数化 SQL，ILIKE 转义 | ✅ 扎实 |
| **行情基准** | 三级降级链，中位价抗污染 | ✅ **扎实** |
| **性价比打分** | ratio → 分段插值 | ⚠️ **缺下限惩罚**（D-3） |
| **车况打分** | 三子项加权 | ⚠️ **口径混入非车况**（D-4） |
| **时效打分** | update_date → age_days | ❌ **量的不是挂牌时长**（D-1） |
| 热度打分 | log1p + P95 归一 | ⚠️ 区分度偏低（P2-1） |
| **模糊量（左右）** | near 维 0.20 权重 | ❌ **退化成准硬过滤**（D-2） |
| 缺维归一 | 从分母去掉 | ✅ 方向对，残留偏差（见 §1.3） |
| 综合排序 | 加权平均 + 同分便宜优先 | ⚠️ 见 P2-3 |
| 解释层 | 确定性模板 + 可选润色 | ✅ 扎实（坚持「只用有依据的数字」是对的） |

### 值得肯定的三个设计

1. **「大模型只做两头，中间不打分」**——排序完全确定性，可复现可回归。这是正确的架构选择，比让模型打分靠谱得多。
2. **「左右」不做硬过滤**——虽然权重配错了，但**没有**产生 `price_min/max` 这个决定是对的。实测确认了这一点。
3. **行情中位价的抗污染性**——实测去掉最低 10% 后中位价只变动 **+3.7%**（见 §1.1），说明中位数这个统计量选对了。

### 缺失的能力（用户没提但业务上可能需要）

| 缺失项 | 说明 |
|---|---|
| **下架/在售状态判断** | 只按 `vehicle_status=1` 筛，但没有「挂牌多久没更新 = 可能已售」的逻辑。结合 D-1 的 `update_date`，其实**可以**做这个判断——但当前它被误用于时效打分 |
| **同车型跨年份的「折旧曲线」** | 现在按固定 5 年桶比价。若能拟合「同车系折旧曲线」，可以判断一台车相对同年份是否偏离趋势线（比现行中位数法更细） |
| **卖家类型（车商/私人）** | 车商价 vs 私人价的可比性不同，现在混在一起算中位价 |
| **「已售」数据反哺行情** | `vehicle_status=2`（已售 ⚠️**4,578** 台）被完全忽略。已售价格是**真实成交**的强信号，比在售报价更可靠——行情基准只用在售（注释说是刻意为之「掺进已售会把中位价往下拽」），这个理由成立，但已售数据**单价**可以用来校准折价率 |

## 5. P2 优化项

### P2-1 · 热度维区分度偏低

```
热度归一后分位：
   P 5.0 = 0.381    P50 = 0.646    P95 = 0.923
   P25.0 = 0.528    P75 = 0.763    P99 = 1.000
```

93.3% 的车落在 0.1–0.9 区间（比预想好），但**中间 50% 的车挤在 0.528–0.763** 这 0.235 宽的带里。标准差 0.163 是**所有维度最低**。

`log1p` 压缩对右偏分布是对的，但 **P95 归一 + log1p 双重压缩**后区分度损失较大。且 `view_count` 原始分布是 `P50=344, P95=2721, max=16715`——**P50 已经是几百**（不是长尾冷启动），log1p 的压缩收益有限。

> 考虑：热度只是 0.04 权重，影响不大。**不建议优先改**。

### P2-2 · `market_stats` 样本分布长尾

```
只统计年份段组（year_bucket >= 0，共 2,191 组）—— 不含 1,272 条车型级全段行：

1-4 台（不足 MIN_SAMPLES=5，不用于比价）   1,486 组   覆盖 2,437 车
5-9 台                                      275 组   覆盖 1,822 车
10-29 台                                    279 组   覆盖 4,686 车
>=30 台                                     151 组   覆盖 12,549 车
```

> ⚠️ 口径说明：若把 `year_bucket = -1` 的车型级全段行也算进来（总 3,463 组），
> 分布会变成 `1-4 台 2,273 组 / 5-9 台 437 组 / 10-29 台 459 组 / >=30 台 294 组`。
> 上表用的是**年份段组**口径，因为降级链真正查询的是这一层。

**1,486 个车系年份组样本 < 5 台**（覆盖率不足），这些车要么走 `near` 要么走 `model` 降级（合计 5.4%）。其中车型级兜底有 557 台——**跨年代比价会失真**，解释层已如实标注「可信度低」，这个是诚实处理，可接受。

### P2-3 · 同分排序规则在非 score 模式下不一致

```python
SORT_PRICE_ASC:  key = (price is None, price, -score)      # 便宜优先，同价看分
SORT_NEWEST:     key = (age_days is None, age_days, -score) # 新优先，同新度看分
SORT_SCORE:      key = (-score, price or 0)                 # 分优先，同分便宜优先
```

`SORT_SCORE` 的同分规则用 `price or 0`——**`price` 为 None 时按 0 处理**，会排到最前。虽然 SQL 层已过滤 `current_price IS NOT NULL`，所以实际不可达；但这条与另外两个分支的 `(x.price is None, ...)` 写法不统一，属于**潜在不一致**。

### P2-4 · `exclude_anomaly` 是布尔开关，无法表达灰度

现在只有「全剔」和「全留」两态：

```python
exclude_anomaly: bool = True    # 默认剔除 ratio < 0.5
```

而实际情况是**连续谱**：ratio 0.45（很可疑）、0.55（有点可疑）、0.65（正常便宜）。建议改成可传阈值（如 `anomaly_ratio: float | None = 0.5`），或者把 D-3 的修复做进打分里（见下）。

## 6. 修复建议（按优先级）

### 针对 D-1（时效维）——两个方向，需要业务决策

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 换语义** | 时效维改用「**挂牌时长**」，需要拿到真实挂牌日。数据里没有这个字段——`created_at` 是迁移日（2026-03-10 重置过），`update_date` 是抓取批次。**要真做，得改爬虫去抓列表页的"发布日期"** | 根本解决，但要动爬虫 |
| **B. 降权/撤维** | 承认现在量的是「最近被爬到」，**把 0.16 权重降下来**（如 0.06），把腾出的权重给性价比/车况 | 立即可做，但放弃了「新车优先」这个有用的信号 |
| **C. 改用批次修正** | 保留 `age_days`，但在打分层按**批次**而不是连续天数算（识别出「最近一批」「上一批」两档） | 保留部分信号，但不彻底 |

> **我的建议：B（先止血）+ A（后续根治）**。因为当前这个维度**在系统性地惩罚 54% 的车**
> （11,604 台时效分 ≤0.45），继续给它 0.16 是在放任偏差。而降权是零风险的——不影响其他任何逻辑。

### 针对 D-2（near 维）——降低权重并缩放

```python
# 现状
WEIGHTS = {"match": .28, "value": .20, "near": .20, "fresh": .16, "condition": .12, "heat": .04}

# 建议：near 降到真正的 "boost" 量级
WEIGHTS = {"match": .28, "value": .22, "near": .08, "fresh": .14, "condition": .20, "heat": .08}
```

关键不是具体数字（那要调参验证），而是 **near 必须显著低于 value**，否则「偏好」就是「约束」。

**注意**：改权重会打破 `test_search.py [9][10]` 的等比缩放断言（那条断言锁的是「0.8 比例」）。改权重时**必须同步改断言**，并重跑 `eval_search.py` 确认 43 例门禁仍绿。

**更好的方案**：保留 near 的 0.20，但把它从「独立维度」改成「**对 value 维的加权调制**」——即让 near 影响性价比分的呈现，而不单列一维。这样语义更准：说「50万左右」时，用户想要的是「在这个价位里找性价比最高的」，而不是「只要接近 50 万就行」。

### 针对 D-3（性价比下限）——加「可疑折损」

`VALUE_ANCHORS` 前段改成**单调下降后再回升**（U 形），或直接给极低 ratio 打折：

```python
VALUE_ANCHORS = (
    (0.30, 0.75),   # 便宜 70% —— 太离谱，反而扣分（可能是问题车）
    (0.45, 0.90),   # 便宜 55% —— 略降
    (0.60, 1.00),   # 便宜 40% —— 峰值
    (0.85, 0.88),
    (1.00, 0.70),
    (1.15, 0.48),
    (1.40, 0.20),
    (2.00, 0.00),
)
```

配合 `tags` 里已有的「⚡ 低于行情 X%（需核实车况）」提示——但现在这个提示**没进分数**，只在标签上。修复后逻辑就自洽了。

### 针对 D-4（车况口径）——拆出独立维度

`import_type` 移出 `condition`，作为独立的小权重维度（或并入「车况」但**不与手数/里程同时满权**）。关键是「只填行货」不该等于「车况满分」。

最小改法：`CONDITION_WEIGHTS` 里把 `import` 的 0.20 降到 0.10，并要求**至少有一个真实车况子项（手数或里程）才给满分**。

## 8. 结论

**骨架是对的，四个地方配错了。**

最该马上处理的是 **D-1（时效维量的不是挂牌时长）** 和 **D-2（near 权重让软偏好变成准硬过滤）**——这两个都是「代码在正确地执行一个错误的配置」，且影响面覆盖所有查询。

D-1 的根因值得单独强调：**这不是算法问题，是字段语义问题**。`update_date` 是「站点更新日期」，被当成了「挂牌日期」。数据本身没错，错在用法。而它带来的偏差是**系统性的**——**54% 的车（11,604 台）时效分 ≤0.45，其中 30.4% ≤0.25**，它们每天都在被这个维度扣分，与真实新旧无关。加上 `fresh` 覆盖是 100%（没有车能靠缺维躲开），**这是当前影响面最大的单一缺陷**。

D-2 的根因则是**注释与实现的分歧**：注释引用 Google 的 soft filter 原则来论证「不该硬过滤」，做对了；但权重配置（0.20，与性价比等权）让软偏好退化成了事实上的硬过滤，实测 Top10 重合度 **0/10**。**设计意图没有被实现层贯彻。**

D-3 / D-4 属于口径与边界问题，改动较小但会影响推荐质量，建议一并处理。
