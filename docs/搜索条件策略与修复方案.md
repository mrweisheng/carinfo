## 1. 业界调研结论（对本项目的映射）

| 来源 | 做法 | 对本项目的启示 |
|------|------|----------------|
| [Google Vertex AI Search：自然语言条件过滤](https://docs.cloud.google.com/generative-ai-app-builder/docs/natural-language-queries) | 从自然语言抽取的条件**默认是硬过滤**（必须满足）；「如果结果不够多，改用软过滤（`SOFT_BOOST`）」——符合条件多的排前面，**部分符合的照样返回、只是靠后** | 正是本项目 near 维（左右偏好）的设计依据；同时给出零命中的正确出路：**硬→软降级**，而不是删条件。→ §4 协议的松绑后「降级为加分」采用此模式 |
| [Google：boost 是软过滤](https://docs.cloud.google.com/generative-ai-app-builder/docs/media-recommendations-boost-bury) | "Boost is a soft filter" —— 软过滤=排序信号，硬过滤=召回门槛 | 条件四层模型（§3）的理论基础 |
| [Algolia：查询放宽与作用域](https://www.algolia.com/blog/ux/query-relaxation-and-scoping-as-part-of-semantic-search) | 放宽顺序：错字容错→复数/词干→同义词→**逐词丢弃**；另一个等价做法是「全部词变可选，按命中词数排序」；⚠️ **放宽必须透明**——暗示「这些就是你要的」会伤信任（Gucci 查出 Uniqlo 的例子） | 「按满足条件数排序」= 我们打分体系里 match/near 维的自然延伸；「透明」= 放宽说明必须进 summary 首句（现已做到，保持） |
| [Elastic Search Labs：自动纠错查询（LlamaIndex Workflows）](https://www.elastic.co/search-labs/blog/llamaindex-workflows-with-elasticsearch) | 合法查询零命中时，**逐个去掉过滤条件重试**，把「去掉哪个能有结果」作为建议返给用户 | §4 的 COUNT 探针 + 逐条件诊断报告直接采用此模式 |
| [Autotrader 等车平台](https://autotrader.com) / [UX 空态实践](https://ux.stackexchange.com) | 筛选项带**实时计数**防死路；零结果页必须明说 + 提供一键放宽；建议**邻近年份/同系变体**替代 | 诚实 0 的提示从「最便宜 X 万」升级为「去掉『行货』还有 3 台 / 邻近年份有 N 台」的**可决策数字** |

一句话总结业界共识：**身份类条件（车型）绝不顶替；属性类条件在零命中时按绑定强度从弱到强降级为软信号，每次降级都对用户透明；实在无解就给可决策的数字，不给死路。**

> ⚠️ **v2 补充的一条限定**（审核发现）：软过滤的「部分符合」在**离散/类别条件**上
> 有个硬边界 —— 当零命中由**单个条件**造成时，放宽该条件后**不存在任何满足它的
> 结果**（可证明，见 §4.5）。所以「满足原条件的排在前面」只在**同时放宽 ≥2 个
> 条件**时才可能兑现；单条件放宽只能做到「如实说明 + 不再要求它」。

## 3. 策略核心：条件四层模型

每个可解析条件归入一层，**层决定它在「部分不满足」时的待遇**：

| 层 | 条件 | 全满足时 | 部分满足/零命中时 |
|----|------|----------|-------------------|
| **L1 身份层** | base_model、变体集（LM350H）、brand、family、model_keyword（真型号） | match 维打分（等值 1.0） | **永不丢弃、永不顶替**。车型在库里没有 → 诚实 0 + 数字提示。放宽只发生在「身份的合法邻域」：同款变体（已做）、±年（见 L2） |
| **L2 强意图数值层** | 年份区间、价格区间 | 硬过滤 | 年份：精确年份零命中时 **±3 放宽并声明**（已做）；**区间年份零命中时不动**（v2 修订，见 §4.1）；价格：**永不放宽**（说 30 万就是 30 万），但提示给到「最便宜 37.8 万，**超预算 26%**」的可决策粒度（B-7 增强） |
| **L3 弱意图属性层** | **import_type、mileage_max、hand_max**（v2 修订：仅这三项） | 硬过滤 | 零命中时**最先松绑**：这些条件经常因**数据覆盖率低**误杀查询，不是用户意图不匹配。松绑后**降级为加分**（Google SOFT_BOOST 模式），不是简单丢弃 |
| **L4 偏好层** | price_near、year_near、displacement | 加分 | 从来不过滤（已做，保持） |

### 3.1 L3 的成员与顺序（v2 用实测覆盖率重写）

**必须用真实覆盖率标定，并且不要照搬 CLAUDE.md 里正则时代的旧数。** 实测
（本库 23,323 台可见车 = 在售 + 有价 + 有联系方式，2026-09-28）：

| 条件 | 有值台数 | 覆盖率 | 是否入 L3 | 松绑序 |
|------|----------|--------|-----------|--------|
| `import_type`（行/水货） | 7,545 | **32.4%** | ✅ 入 | **1**（最缺 → 最可能误杀 → 最先松） |
| `mileage_max`（里程） | 10,281 | **44.1%** | ✅ 入 | **2** |
| `hand_max`（手数） | 16,075 | **68.9%** | ✅ 入 | **3** |
| `transmission`（波箱） | 23,323 | **100%** | ❌ **不入** | — |
| `seats`（座位） | 23,323 | **100%** | ❌ **不入** | — |

**v1 的两处硬伤**：
1. 「手数仅约 15%」是 CLAUDE.md 里**正则时代**的旧数（早被 LLM 提取抬到 68.9%），
   这个前提不成立；
2. v1 自述「按实测数据覆盖率升序」，但它给出的顺序 `hand → mileage → import` 与
   覆盖率升序**恰好相反**（正确是 `import → mileage → hand`）。

**`transmission` / `seats` 为什么不进 L3**：它们是 `vehicles` 的**表列**，覆盖率实测
**100%**（20 年前后的写法差异早已归一）。L3 的立论是「不符 = 字段缺失导致误杀」，
对它俩完全不成立 —— 用户明说「七座 / 自动波」时放宽就是返回不符条件的车，是
**语义倒退**，不是数据补丁。归入「**永不放宽**」，只能在诚实 0 的提示里说明。

> 顺带验证 B-7 的例子：LM350/LM350H 全量 61 台，2021 年 16 台（7 座 11、行货覆盖 7），
> 约束确实落在手数/里程/行货上 —— **不碰 seats 也够用**，正好支持这条修订。

**松绑顺序（绑定强度从弱到强）**：
`L3: import_type → mileage_max → hand_max`（实测覆盖率升序）→ `L2 精确年份 ±3`
→ `L2 价格不松绑改提示` → `诚实 0 + 逐条件诊断`。

这个分层的判定依据是**「条件杀死查询的原因」**：
- 身份不符 = 库里没这车 → 用户需要知道「没有」，顶替有害；
- 年份不符 = 空窗/换代 → 邻近年份大概率满足意图，±3 合理；
- 预算不符 = 强意图 → 不擅自突破，给数字让用户自己决定；
- L3 属性不符 = 多数时候是**字段缺失**（`extra_fields` 提取覆盖率 32–69%），
  不是真不符 → 降级为排序信号最合理；
- `transmission`/`seats` 不符 = **真不符**（字段 100% 有值）→ 不许放宽。

## 4. 统一零命中协议（替换现有 `search_with_fallback` 阶梯）

### 4.1 协议

```
Step 0  全条件硬查（现状）
        total > 0 → 返回（结束）

Step 1  【L3 松绑·降级为软信号】（新增，B-7）
        按 import_type → mileage_max → hand_max 顺序，**累积式**逐个从硬过滤移除，
        每步先做一次 EXISTS 探针（最便宜，实测 47–62ms）：
          drop(import) 无命中 → 再 drop(import+mileage) 有命中 → 停（最小移除集）
        命中后：用放宽后的条件重查，被松条件转入第七维「松绑补偿」打分
        （每放宽一项，满足它的车按比例加分 —— Google SOFT_BOOST 模式），
        返回 + note「库里没有满足『水货』的车，已放宽这个条件；以下结果不再要求它」。
        ⚠️ 单条件松绑时**不承诺**「满足原条件的排在前面」（可证明不存在这样的车，
           见 §4.5），文案只说「已放宽」。

Step 2  【精确年份 ±3】（现状步骤 1/2/3 保留）
        精确年份零命中 + 关键词在场 → 保身份、年份 ±3 重查（现状）。
        ⚠️ **区间年份（min≠max）不做放宽**（v2 修订，理由见下）。

Step 3  【噪声关键词丢弃】（现状步骤 2 收紧，B-2）
        只允许丢弃「既非身份码、也不是任何库内车系键前缀」的关键词。
        '保姆车' → 不是任何键前缀 → 噪声，可丢；
        '740' → 是 740LIA/740LI/740I 的前缀 → 真型号，**不许丢**。
        （判定：`spec.keyword_is_identity`（解析层用 `ctx.is_model_code` 盖章）
          OR `engine.is_identity_code`（含字母的 ASCII 码，如 M760））

Step 4  【价格探针】（新增，只提示不放宽）
        有 price_max 且仍 0：探「去掉价格后的数量 + 最低价」。
        提示「没有 XX 万以内的 LM350，最便宜 HK$37.8 萬（超预算 26%），
        共 N 台在不限价时符合其余条件」。

Step 5  【诚实 0 + 逐条件诊断】（现有 _target_hint 增强）
        身份数字提示（年份段/最低价，现状保留）+ 逐条件探针数字：
        「去掉『行貨』还有 3 台；去掉『一手』还有 5 台」——用户自己挑着改口。
```

#### ⚠️ v2 修订：为什么去掉「区间年份两端各 +1 年」

v1 在 §4.1 Step 2 写了「区间年份 → 放宽两端各 +1 年」，同时又在 §0/§6 断言
`2016到2017年的宝马740` 应当 **total_matched == 0**。这两条**互相矛盾**：

实测 `car_model ILIKE '%740%'`（可见池）年份分布：
`2010:1, 2011:2, 2013:2, 2014:3, 2015:1, 2018:7, 2019:5, 2020:1, 2021:1, 2023:3, 2024:1, 2025:1`
—— **2015 有 1 台、2018 有 7 台真 740**。

所以一旦给区间两端各 +1 年，这个查询就会返回 15/18 年的车，**不再是诚实 0**，
§6 的断言必然挂。更关键的是，这已经是**真的顶包**：用户要 16-17 年，系统回 15/18 年。

**v2 选择：去掉区间 ±1。** 理由：
1. 区间放宽**没有可信的带宽依据** —— 精确年份的 ±3 来自「换代空窗」的实测
   （库内 7 系 16/17 年空窗），区间是用户自己划的范围，擅自在两端各外扩 1 年
   更像是「猜」；
2. 诚实 0 + 年份段提示（「库里 740 有 2010-2011、2013-2015、2018-2021…年的车」）
   已经足够可决策；
3. 与 §6 的可回归断言一致（断言必须可复现，不能靠"碰巧没命中"）。

### 4.2 全场景决策矩阵（「应该怎么返回」的最终口径）

| 场景 | 返回 |
|------|------|
| 全条件满足 | 直接返回，按七维分排序（现状 ✓） |
| 身份+年份满足，预算超 | 诚实 0 + 超预算幅度 + 不限价时的满足数（Step 4） |
| 身份满足，L3 属性杀死 | 松绑 L3（最小移除集）→ 返回 + 声明（Step 1） |
| 身份满足，**精确**年份空窗 | 保身份 ±3 年 + 声明（现状 ✓，`17年的宝马740` 实测 16 台） |
| 身份满足，**区间**年份全空 | **不放宽** → 诚实 0 + 年份段提示（v2 修订） |
| 变体差异（用户说 LM350，库里有混动） | 变体合并 + **同分**（Fix-5） |
| 车型完全不在库 | 诚实 0 +「库里没有 X；最便宜的{品牌}约 Y」（现状 ✓，M760 实测；**两条路径一致**，规则路径靠形状补救，见 §5 Fix-2b） |
| 关键词是解析噪声（'保姆车'/'LM'） | 丢弃重查 + 声明（现状 ✓；真型号永不进此分支） |
| 条件太宽 | ScanTooWide → 400 提示收窄（现状 ✓，不在本协议范围） |

### 4.3 结构化输出（API/MCP 同步）

`SearchResult` 增加 `relaxed: list[str]`（如 `["hand_max", "mileage_max"]`），
由 `search_with_fallback` 填写 → `explain()` 透传到 `ExplainedResult.relaxed`
→ `/search` 与 MCP `search_cars` 的每组 payload 带 `relaxed`
（`query_groups[].relaxed`；单组时在顶层）。现状的自然语言 fb_notes 保留
（人话仍进 summary 首句），`relaxed` 字段给 Agent/前端做结构化消费（徽标、
一键按原条件收紧）。

### 4.4 探针成本（v2 实测，替换 v1 的「<100ms」）

实测（本库 2.3 万可见车，2026-09-28）：

| 探针口径 | 单次耗时 | 用途 |
|----------|----------|------|
| ① `build_query` 包一层 `count(*)`（含窗口函数） | **98–172ms** | 不采用 |
| ② 裸 `count(*)`（去掉窗口函数） | **48–109ms** | 要**数字**时（诊断文案） |
| ③ `EXISTS(SELECT 1 … LIMIT 1)` | **47–62ms** | 只要**命中判否**时（L3 累积探针） |

> v1 写的「≤5 次探针、总增量 <100ms」**不成立**。参考基线：一次正常
> `search()` 约 0.9–1.0s（全量拉候选进内存打分），一次零命中端到端约 1.5s。

**v2 的成本口径**：Step 1 最多 3 次 EXISTS 探针（≈50ms/次）+ 1 次完整重查；
Step 5 最多 4 次 COUNT 探针（≈50–110ms/次）。最坏一轮约 **400–700ms**，
**只在已经 0 命中的路径上付**（正常查询 = 一次 `search`，不变）。
实现上用 `_where_clause` 把过滤条件抽成**单点**，主查询与探针共用同一份口径 ——
两处各写一份必然漂移，而漂移的后果是「探针数字与实际检索不一致」。

**降级**：任何探针异常都当「没有命中 / 无数字」（`_probe_exists` / `_probe_count`
内 try/except）。提示是锦上添花，**绝不能因为它出错就把一次本来正常返回 0 的
查询变成 500**。

### 4.5 「部分满足」的硬边界（v2 审核新增的关键发现）

**命题：若零命中由单个条件 C 造成，则放宽 C 之后的可用集中，满足 C 的车必然为 0 台。**

证明：零命中 ⇔「满足全部条件的车集为空」。设 R = 满足「除 C 外全部条件」的车集。
若 R 中存在满足 C 的车 r，则 r 满足全部条件 → r 属于空集，矛盾。∎

实测印证：`LM350 + 水貨 + 一手` 松绑 `import_type` 后 32 台，第七维分值**全为 0.0**。

两条推论，均已落到实现：
1. **第七维加门控 `len(relaxed) >= 2`** —— 单条件松绑时它恒为 0，让它参与只会把
   总分按 `1/(1+0.08)` 无谓稀释（排序不变、分数变小），不如缺席；
2. **单条件松绑的 note 不许说「满足原条件的排在前面」** —— 那是一句不可能兑现的话。
   只说「已放宽这个条件；以下结果不再要求它」。

只有当**累积放宽 ≥2 个条件**时才有部分满足（如「行货 + 一手 + ≤5万公里」三项
一起杀死查询、最终全放宽，则同时满足其中两项的车拿 0.5 分）。

### Fix-1（P0，B-1）parser 截断防呆：压平组门控 — `parser.py` `_group_to_spec`

压平组只有**本身是已知车型**时才参与截断判定：

```python
# 现状：所有空格相连 ASCII 段都压平加入 tokens → "740 2018"→"7402018" 误判 '740' 截断
for grp in re.findall(r"[A-Z0-9]+(?:\s+[A-Z0-9]+)*", query.upper()):
    flat = re.sub(r"\s+", "", grp)
    if flat not in tokens:
        tokens.append(flat)

# 改为：只有压平结果是已知车型键/词表前缀命中才加入
for grp in re.findall(r"[A-Z0-9]+(?:\s+[A-Z0-9]+)*", query.upper()):
    flat = re.sub(r"\s+", "", grp)
    if flat not in tokens and (flat in ctx.models or ctx.vocab.match_compact(flat)):
        tokens.append(flat)
```

**口径统一（v2 修订）**：正文只写**实际被调用的方法** `ctx.vocab.match_compact`
（v1 正文写 `vocab.match`、代码写 `match_compact`，两者恰好同结论，但会误导后续维护）。

已验证数据支持：`'LM350' in ctx.models`=True（仍能拦 `'LM 350'`→`'350'` 真截断）；
`'7402018' not in ctx.models` 且 `vocab.match_compact('7402018')` 为 `None`（不再误拦）。
副作用：库外长尾车型带空格写法漏判截断 → 关键词保留 → **查宽，是安全方向**。

**回归风险**：词表变动后 `flat` 的判定集会变，需在 §6 保留「`LM 350` 仍被拦」的断言。

### Fix-2（P0，B-2）真型号判定贯通 parser→engine

1. `SearchContext` 加方法（`context.py`）：

   ```python
   def is_model_code(self, kw: str | None) -> bool:
       """关键词是否指向库内真实车型：等值键、或某键的前缀（>=2 字符）、或词表命中。"""
       if not kw:
           return False
       k = kw.strip().upper()
       if len(k) < 2:
           return False
       if k in self.models or self.vocab.match_compact(k):
           return True
       return any(m.startswith(k) for m in self.models)
   ```

2. `SearchSpec` 加字段 `keyword_is_identity: bool | None = None` ——
   **不进** `ALLOWED_LLM_FIELDS`（模型不可注入），走 `_coerce_opt_bool` 三态收敛。

   ⚠️ **v2 补充的风险说明**：`SearchSpec.from_dict` 用的是 `dataclass_fields`
   **全量白名单**，所以 `/search/spec` 与 MCP `search_by_spec` 的**程序化调用方
   可以传该字段**。误设为 `True` 会锁死「噪声关键词不许丢弃」，让零命中查询退不
   回放宽结果（例如 `keyword='保姆车'` + `keyword_is_identity=True` → 诚实 0 而不是
   丢弃重查）。**这是程序调用方可控的风险点，不是模型可注入点** —— 已在字段
   docstring 里写明。

3. parser `_group_to_spec` 与 `rule_based_parse` 末尾都盖一次章：
   `payload["keyword_is_identity"] = bool(ctx.is_model_code(keyword))`。

4. engine 侧：`_identity_keyword(spec)` = `spec.model_keyword`
   当 `spec.keyword_is_identity or is_identity_code(spec.model_keyword)` 时，否则 `None`。
   （`_is_identity_code` v2 更名为公开的 `is_identity_code`，`engine` 与 `parser`
   各自贡献一半，**不做跨层 import**：解析层管「库内真型号（含数字前缀）」，
   引擎管「含字母的 ASCII 码」。）

5. **订正 `_is_identity_code` 的错误注释**：「740 会先在 ctx.models 等值命中」
   实测为假（`'740' not in ctx.models`）。

效果：`2016到2017年的宝马740` → `740` 不再被当噪声丢弃 → 走 Step 5 诚实 0 +
`_target_hint`（ILIKE %740% 能对到 740LIA）→「740 库里有 2010-2025 年的车
（不含 2016-2017），最便宜约 X」。**实测修复后 total_matched == 0。**

### Fix-2b（P0，B-8）规则降级路径：型号识别 + 年份区间 — **v2 新增**

v1 完全没有覆盖这条通道（Fix-1/Fix-2 只作用于 LLM 路径）。两处补齐：

1. **型号关键词补救**（放在 family 识别之后 —— 放在前面会让
   `not payload.get("family")` 门控恒真）：

   ```python
   if not payload.get("base_model") and not payload.get("family"):
       for _m in re.finditer(r"[A-Z0-9]+", up):
           tok = _m.group(0)
           if len(tok) < 3 or tok in ctx.models:
               continue                      # 完整键上面的扫描已处理
           if _QUANTITY_RE.fullmatch(tok):   # '3000CC' 排量写法，不是型号
               continue
           after = up[_m.end():_m.end() + 3].lstrip()   # 单位前瞻：向后看 3 字符
           if after[:1] and after[:1] in "萬万億亿千kKwW公里座坐年手匹":
               continue                      # '50萬' 的 50、'2018年' 的 2018 不是型号
           if after[:2] in ("CC", "KW", "HP", "PS", "NM", "KM"):
               continue                      # '3000 cc'（空格分隔的排量写法）
           if _YEAR_RE.fullmatch(tok):
               continue
           if ctx.is_model_code(tok) or _CODE_SHAPE_RE.fullmatch(tok):
               payload["model_keyword"] = tok
               payload["keyword_is_identity"] = True
               break
   ```

   - `after[:1]` 的**空串判断不能省**（`'' in "萬万…"` 为 `True`，会漏掉句尾的型号）；
   - **排量守卫必须排在 `is_model_code` 之前**（v2.1，见下）；
   - `_CODE_SHAPE_RE = [A-Z]{1,3}[0-9]{1,4}` 是**库外型号**的形状补救（v2.1）。

2. **年份区间解析**（`2016到2017年` / `14-17年` → `year_min/year_max`）：
   现状只认「数字后紧跟『年』」的裸年份，`2016` 后面是「到」→ 被忽略，
   只剩 `2017` 被锁成精确年，**区间语义被悄悄缩成单年**。区间块要跑在
   单年循环**之前**，并让单年循环跳过区间 span 内的年份。

效果：`宝马740 2018年` → kw='740' → **6 台全部含 740**（原 229 台顶包）；
`宝马740 50万以内` → **22 台全含 740**（原 1,838）；`2016到2017年的宝马740`
→ 区间正确表达 → **0 + 数字提示**（原 175 台顶包）。

**库外型号的形状补救（v2.1 新增，收窄能力边界）**：
`宝马M760` 这类**库里既不存在、也不构成任何键前缀**的型号，`ctx.is_model_code`
判不出（它只有库内证据）。v2.1 追加一条**形状**判据
`_CODE_SHAPE_RE = [A-Z]{1,3}[0-9]{1,4}`（且 `len≥3`）：命中即按身份关键词处理。

- 效果：规则路径 `宝马M760` → kw='M760'、identity=True → **诚实 0**
  （原 1,959 台品牌级），与 LLM 路径**行为一致**（§6 断言已由「仅 LLM」改为「两者」）；
- 不误伤：`len≥3` 挡掉 `'V6'/'W12'` 这类引擎排布短词；字母 >3 的
  `'SDRIVE18IA'` 天然不匹配；
- 仅在 base_model / family 均未识别时才启用（与既有门控一致）。

**排量守卫（v2.1 新增；修一处自审发现的活 bug）**：
`'3000cc'` 会被 `[A-Z0-9]+` 切成整 token `'3000CC'`；而词表松匹配
（`match_compact`）把 `'3000'` 命中 HINO 的 `'300'` 前缀模式，使
`is_model_code('3000')` 返回 **True** → `'3000cc 宝马'` 被锁成
`model_keyword='3000CC'` → **0 台 + 误导提示**（实测）。原以为
「库里没有 3000 开头的键」能兜住 —— **不成立**（真正在兜的是词表前缀匹配，
而它兜不住）。修法：`_QUANTITY_RE`（数字 + CC/KW/HP…）+ 单位前瞻向后看 3 字符
（覆盖 `'3000 cc'` 的空格写法）。实测修复后两条写法都回归品牌级、不再 0 台；
**两个守卫缺一不可**（变异测试：关掉 `_QUANTITY_RE` → `'3000CC'` 又被误提升）。

### Fix-3（P2，B-3）family 裸键 — `engine._where_clause`

```python
pat = f"^(M-?)?{fam}([0-9 ]|$)"     # 原来只有 [0-9 ]，裸家族名（'A6'/'MODEL 3'）漏
```

**v2 补充（v1 漏写的两点）**：
- **OR 分支 `^M{fam}` 未在 v1 中提及**：它兜住 M 前缀高性能版（`fam='7'` → `^M7`
  命中 M760…），**保留**。对 `fam='MODEL 3'` 会拼出永假的 `^MMODEL 3`（无害；
  保留是为了让「M 前缀兜底」这条语义对所有 family 一致）。
- 风险检查（实测）：新分支只多出「car_model 恰好等于家族名」这一类 ——
  `fam='S'`（奔驰）裸键 **0 台**、`fam='7'`（宝马）裸键 **0 台**；
  SL500 / SMART 仍被排除（S 后是 L/M，两个分支都不匹配）✓。
- 效果（完整过滤下）：`A6` 26 → **30** 台、`MODEL 3` 269 → **276** 台，与裸键数完全对齐。

### Fix-4（P2，B-4）规则路径短键 — `parser.rule_based_parse`

`if len(model) < 3` → `if len(model) < 2`。纯数字键仍由 `not any(c.isalpha()…)` 拦住
（`'30'/'2015'` 不会误命中），单字符脏键仍被 `len<2` 拦住。
效果：`宝马M3`→M3、`宝马X5`→X5、`奥迪A6`→A6 全部恢复识别（修复前 base_model 全为 None）。

**v2 补充风险面评估**（v1 只举了 M3/X5/Z4 三个例子）：实测会放行
**97 个两位含字母键** —— `A1/A3…A8, C3/C4/C5, EV, GT, RS, RR, LC, M2~M6,
Q2~Q8, S1~S8, T3/T4/T6, TT, X1~X7, Z3/Z4, ZG…`。其中有 `EV / GT / RS / AC / AN`
这类**泛型短词**：用户单独喊「EV」「GT」时会被当成车系。
靠 `(?<![A-Z0-9])…(?![A-Z0-9])` 边界断言挡住子串误命中，但**孤立词**的误判无法
用边界解决。权衡后**接受**（宁可认出也不漏识：`奥迪A6` 是真需求，「EV」单独作为
车系名的概率远低）。**若线上出现「搜 EV 返回一堆 EV 车系」的投诉，改法是给两位键
加「必须与已识别品牌同现」的附加条件** —— 记为已知风险。

### Fix-5（P3，B-5）变体同分 — `engine.score_match`

```python
if spec.base_model:
    keys = spec.base_models or [spec.base_model]
    m = 1.00 if base_model in keys else 0.30
```

**v2 补充：这条改动会让旧代码变成死代码，已一并删除。** 旧实现用
`base_model.startswith(spec.base_model)` 得 0.85，而 SQL 侧早已是
`f.base_model = ANY(base_models)` **等值限定** → 车辆命中的键必然等于列表中的某一项
→ 那条 startswith 分支**永远不会命中**（实测确认）。v1 只说「建议一并清掉」，
v2 直接删掉并在注释里写明原因。

### Fix-6（P3，B-6）词形补充 — `parser` + `SYSTEM_PROMPT`

`SYSTEM_PROMPT` 值规则行补：`「一手/一部手/首任车主」→ {"hand_max": 1}`；
规则层 `"一手" in hand_text` 之外补 `"一部手"` / `"首任車主"` / `"首任车主"`。

**v2 补充（优先级与事实）**：这是**用户输入侧**的口语覆盖，不是提取侧的能力提升 ——
实测描述语料里 `'一手'` 165 条、`'一部手'` **0 条**、`'首任'` **1 条**。
优先级最低，**不与两个 P0 混批次**（见 §7）。

### Fix-7（P1，B-7）统一零命中协议落地 — `engine.search_with_fallback`

按 §4.1 重构，保持函数签名不变（`(conn, spec) -> (SearchResult, list[str])`，
API/MCP 四个调用点零改动即获得新行为）。实现要点（v2 修订后的实际口径）：

- **`_where_clause()` 单点**：主查询与探针共用同一份过滤条件；
  `_exists_sql` / `_count_sql` 在其上包一层，避免两处口径漂移；
- 探针口径与成本见 §4.4（EXISTS 判否 / COUNT 要数字 / 探针异常一律降级）；
- Step 1 的松绑结果写进 `SearchResult.relaxed`，并触发**第七维**（见下）；
- `explain` 的零结果文案（含自审补充）：
  - **有车型目标时删掉「建议放宽预算或年份」**这句空话（具体数字已由 fb_notes
    拼在 summary 首句）；且收敛句由「库里没有符合『740』条件的车」改为
    「没有『740』能同时满足你这些条件」—— 旧句会与前置的「不限年份还有 27 台」
    打架，被读成「库里根本没有 740」。否定的是**条件组合**，不是车型本身；
  - **无车型目标时**（如「50万以内的7座MPV」）返回「库里没有符合条件的车。
    建议放宽预算或年份。」—— 避免旧逻辑拼出「符合『全部车型』条件」的别扭话。

**第七维「松绑补偿」（v2 关键修订，替换 v1 的「外挂 bonus」）**

- 写进 `WEIGHTS`：`{"relaxed": 0.08}`，`DIM_LABELS` 加「松绑补偿」；
- 分值 = 被放宽条件中**满足的项数 / 项数**，`spec` 取**放宽前**的原始 spec
  （阈值在它身上；放宽后的 spec 字段已置 None）；
- **门控 `len(relaxed) >= 2`** —— 单条件松绑时该维恒为 0（§4.5 证明），
  返回 `None` 让它缺席，避免无谓稀释总分；
- 常态缺席 → `combine()` 的缺维归一把它从分母去掉 → **对既有查询排序零影响**；
- 量级刻意保持弱信号（0.08，与 near 同档）：boost 必须显著低于 match/value，
  否则等于把用户的硬条件偷换成偏好。**它只在校验分接近时改变顺序，不承诺
  「满足原条件的车一定排在最前」**；
- `explain` 的「缺维」叙述改用 `CORE_DIMS`（核心六维）—— 否则每条结果都会多一句
  「缺松绑补偿数据」的噪声；
- ⚠️ **后果：`sum(WEIGHTS)` 变为 1.08**（六维仍为 1.00）。若测试锁了「权重和 == 1.0」
  或锁了 `WEIGHTS` 的键集，**必须同步更新**（§6）。

### Fix-8（P3）预算提示增强 — `engine._target_hint` 输出侧

在「最便宜约 HK$X」之后补超预算幅度：
`(min_price - price_max) / price_max` → 文案「最便宜 HK$37.8 萬（超预算 26%）」。
比「没有符合的」可决策得多（用户据此判断「加点预算」还是「换型号」）。

### 不改的（防止误改）

- `transmission` / `seats` 不进零命中协议（§3）；
- 区间年份不放宽（§4.1）；
- 库外型号（如 M760）两条路径都诚实 0：规则路径靠「型号形状」补救（§5 Fix-2b，v2.1）。

## 6. 回归测试（锁死行为的用例）

**已落地为永久测试**：`tests/`（v2.1，2026-09-29）。分层运行：

```
pytest                  # 全部（离线 77 + 真库 10）
pytest -m "not db"      # 仅离线：合成 ctx + FakeLLM，不连库不联网，<1s
pytest -m db            # 仅真库黄金用例（无库自动 skip）
```

- `conftest.py` 提供 `synth_ctx`（合成词表/键集合，复刻 740 前缀键、HINO 的 `'300'`
  词表模式等关键形状）、`fake_llm`（注入式假模型，不联网）、`real_ctx` / `db_fetch`
  （真库，连不上自动 skip）；
- 下表即这套测试的规格说明（`路径` 列：LLM / 规则 / 两者 / 单元 / **真库**）。

| 用例 | 断言 | 路径 |
|------|------|------|
| `宝马740 2018年`（假 LLM 给 keyword=740） | `spec.model_keyword == '740'`（Fix-1）；命中集**全部** car_model 含 740（实测 6 台） | LLM |
| `宝马740 50万以内` | keyword 保留（Fix-1）；命中全含 740（实测 22 台） | LLM |
| `宝马740 2018年`（无 LLM） | keyword=='740'（Fix-2b）；命中全含 740 | 规则 |
| `2016到2017年的宝马740` | **total_matched == 0**，fb_notes 含「740 库里有 … 年的车」（Fix-2/Fix-2b） | **两者** |
| `17年的宝马740` | 保身份 ±3 放宽，命中含 740 且 fb_note 带 ±3（实测 16 台） | 两者 |
| `雷克萨斯 LM 350`（假 LLM 给 keyword=350） | keyword 被判截断丢弃、规则救回 `base_model=LM350`（Fix-1 不破坏原防线） | LLM |
| `宝马M3` / `宝马X5` / `奥迪A6`（无 LLM） | `base_model` 分别为 M3 / X5 / A6（Fix-4） | 规则 |
| `宝马M760` | **两者**都要求诚实 0 + 提示（规则路径靠 `_CODE_SHAPE_RE` 形状补救，v2.1 起） | 两者 |
| `3000cc 宝马` / `3000 cc 宝马` | `model_keyword is None`（排量守卫）；真库命中 > 0，不静默 0 | 规则 + **真库** |
| `奥迪A6` / `特斯拉Model 3` | 裸键车在命中集内（Fix-3：30 / 276 台，快照） | **真库** |

| `is_identity_code` | `'M760'/'Z8'/'X1'` → True；`'30'/'740'/'2015'` → False（740 靠 ctx 盖章，不靠这里） | 单元 |
| 零命中协议 | patch 掉 `search`/探针，脚本化命中数：L3 累积顺序（import→mileage→hand）、`relaxed` 字段、单/多条件 note 文案 | 单元 |
| **身份永不顶包**不变量 | 「只要关键词还在就 0、丢掉才有结果」—— 若协议丢了身份码，该用例会变成 5（顶包） | 单元 |
| 第七维 | 单条件松绑 → **不出现** `relaxed` 维且文案不含「排在前面」；≥2 条件 → 分值有区分度、进 `score_breakdown` | 单元 |
| 常规查询回归 | 无松绑查询的 `scores` **不含** `relaxed`；`explain` 缺维叙述不含「松绑补偿」；两次调用 Top 顺序与分值一致 | 两者 |
| 零结果文案 | 有车型目标 → 收敛句为「没有『X』能同时满足你这些条件」，且**不含**「建议放宽」；无车型目标 → 「库里没有符合条件的车。建议放宽预算或年份。」 | 单元 |
